Authenticated Access to Platform-Wide Advertiser Directory

A broken access control flaw let any authenticated user read the platform-wide advertiser directory.

Summary

A broken access control vulnerability in a self-service advertising platform allowed any authenticated user to access the platform’s entire advertiser directory through a paginated listing endpoint.

A newly registered account in an “Awaiting Approval” state could browse 72 pages of advertiser records and view information belonging to every advertiser on the platform. At the time of testing, more than 1,400 records were exposed.

The issue was caused by missing authorization controls on a listing action that returned all advertiser records rather than restricting results based on user permissions or ownership.

The platform, hostnames, and identifiers have been redacted. Technical details have been adjusted where necessary to prevent reproduction against the live environment.

Discovery

The target was a legacy CakePHP application exposed within a large wildcard scope.

Registration was open and required only email verification. After creating an account, I was assigned the lowest available privilege level, with an account status of “Awaiting Approval.”

During authenticated testing, an advertiser-related endpoint was identified:

Plain Text

GET /advertisers/index

The endpoint name suggested a standard CakePHP listing action, making it a suitable candidate for access control testing.

Confirming the Exposure

Accessing the endpoint while authenticated returned a paginated HTML table containing advertiser records.

Plain Text

GET /advertisers/index

The response returned HTTP 200 and displayed 20 records per page. Pagination extended across 72 pages, exposing the full advertiser dataset.

Each record contained information including:

  • Advertiser ID
  • Internal user ID
  • Business category
  • Full name
  • Street address
  • Suburb, state, and postcode
  • Account creation timestamps

To verify that the data originated from the production dataset, I located my own advertiser record. The account I had created only minutes earlier appeared on the final page of results, positioned after all existing advertisers.

Unauthenticated requests to the same endpoint were redirected to the login page, indicating that the application considered the data private but failed to enforce authorization once a user obtained any valid session.

Impact

The vulnerability exposed advertiser information that was intended for platform use and not publicly available through normal application functionality.

While reviewing records, I identified several examples demonstrating the sensitivity of the exposed data:

  • A sole-trader advertiser whose personal Gmail address had been entered into a postcode field, exposing information not publicly associated with the business listing.
  • An internal staff test account containing a corporate email address visible to any authenticated platform user.

The primary issue was not a single exposed record but the scale of the disclosure. Any approved or unapproved user could enumerate the directory and access information belonging to all advertisers on the platform.

Testing confirmed a read-only access control issue. No evidence of modification, deletion, or administrative functionality was identified through the affected endpoint.

Given the ease of exploitation, the low privileges required, and the volume of exposed information, the issue was reported as a broken access control vulnerability affecting the confidentiality of advertiser data.

Root Cause

The affected listing action returned platform-wide advertiser records without validating whether the requesting user was authorized to view them.

Conceptually, the logic resembled:

PHP

$advertisers = $this->paginate();

Because the query was not scoped to the current user and the action lacked a role check, any authenticated session could access the full dataset.

The vulnerability was caused by missing authorization controls rather than by the pagination mechanism itself.

Remediation

The following remediations were recommended:

  • Restrict access to the endpoint based on role requirements.
  • Scope advertiser listings to records owned by the authenticated user where applicable.
  • Apply authorization checks at the controller level rather than relying solely on authentication.
  • Review similar scaffolded listing actions throughout the application for equivalent access control issues.

Conclusion

This issue resulted from a missing authorization check on a standard listing endpoint. Any authenticated user, including newly registered accounts awaiting approval, could access the platform’s complete advertiser directory.

Although the vulnerability did not provide modification capabilities, it exposed platform-wide advertiser data, including names, addresses, internal identifiers, and other user-supplied information. The combination of broad data exposure, low attack complexity, and lack of privilege requirements made the issue a clear broken access control finding.
