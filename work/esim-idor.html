Unauthenticated Access to eSIM Activation Credentials via Inventory API IDOR

An unauthenticated authorization flaw in a mobile provisioning inventory API exposed SIM records and eSIM activation QR codes.

Summary

This assessment identified an unauthenticated authorization flaw in the inventory API of a mobile provisioning platform. Two internet-accessible endpoints exposed SIM inventory records and associated eSIM activation QR codes without requiring authentication.

By enumerating sequential record identifiers, an attacker could retrieve SIM metadata belonging to other customers and obtain QR codes containing GSMA LPA activation strings. These strings included both the SM-DP+ endpoint and Matching ID used during eSIM profile provisioning.

The issue was ultimately caused by missing authorization checks on object retrieval endpoints. While the vulnerability itself was a straightforward IDOR, the exposed data included activation credentials rather than inventory metadata alone, significantly increasing the impact.

The vendor and target environment have been redacted. Technical details have been adjusted where necessary to prevent reproduction against the remediated service.

Discovery

The target was part of a large wildcard scope containing several thousand internet-facing assets. Initial reconnaissance focused on identifying services likely to support internal operations rather than public users.

One hostname containing inventory-related terminology exposed a small JSON API over HTTPS. Requests to several endpoints returned structured data without requiring authentication, API keys, or session cookies.

At this stage there was no vulnerability, only an observation: inventory-related functionality was publicly reachable and responding to anonymous requests.

Further inspection revealed an endpoint that accepted a small integer identifier and returned information relating to individual SIM records. The identifiers appeared sequential and responses differed between records, indicating the endpoint was performing lookups against live inventory rather than returning static content.

This suggested a possible authorization issue and became the primary hypothesis for testing.

Confirming the Exposure

The inventory endpoint returned SIM-related information, including identifiers associated with provisioned subscriptions.

A separate endpoint accepted one of these identifiers and returned a PNG image. Initially the response appeared unremarkable; however, decoding the QR code revealed a GSMA LPA activation string:

Plain Text

LPA:1$<smdp-plus-host>$<MatchingID>

This format is used during consumer eSIM provisioning and contains the information required for a device to retrieve an eSIM profile from the relevant SM-DP+ server.

At that point the issue moved beyond simple information disclosure. The API was not exposing inventory metadata alone; it was exposing provisioning credentials tied to customer subscriptions.

Both endpoints were accessible without authentication, allowing anonymous retrieval of activation artefacts associated with inventory records outside the attacker’s ownership.

Impact Assessment

The strongest part of the finding was not the IDOR itself but the nature of the exposed data.

Three factors drove the severity assessment:

  • Unauthenticated access: both endpoints were accessible without any form of authentication or authorization.
  • Enumerability: records were referenced using sequential identifiers, making large-scale discovery practical.
  • Credential exposure: the QR codes contained valid GSMA activation strings rather than passive data such as status information or identifiers.

During impact validation, I specifically looked for evidence that an unactivated profile could be claimed using the exposed credentials. While I identified numerous eSIM-related records, I did not find a suitable candidate that allowed me to demonstrate profile takeover.

As a result, I did not claim successful subscription hijacking or account compromise. Those outcomes were plausible, but they were not reproduced during testing.

The issue was therefore reported as a High severity finding based on unauthenticated access to telecommunications subscriber data and provisioning credentials at scale, rather than on a demonstrated integrity impact.

Testing was intentionally limited to credential retrieval. No attempt was made to redeem, activate, or install any exposed eSIM profile.

Root Cause

Based on observed behaviour, the affected endpoints performed direct object retrieval without verifying whether the requesting party was authorized to access the returned data.

Conceptually, the logic resembled:

Python

record = inventory.get(id)
return render_qr(record.sim_number)

The vulnerability was not caused by predictable identifiers. Sequential keys only made enumeration easier.

The underlying issue was the absence of object-level authorization controls.

Remediation

The service should require authentication and enforce authorization on every inventory lookup and QR retrieval operation.

Additional recommendations included:

  • Validate access permissions for each requested record.
  • Treat LPA activation strings and Matching IDs as sensitive credentials.
  • Limit exposure of internal provisioning services through authenticated gateways.
  • Use non-predictable identifiers as defence-in-depth rather than as a primary security control.

Conclusion

This was a straightforward authorization failure on an internet-exposed inventory service. The technical vulnerability itself was an ordinary IDOR, but the exposed data significantly increased the risk.

Anonymous users could enumerate inventory records, retrieve subscriber information, and obtain eSIM provisioning credentials that should only have been available to authorized parties. Although profile takeover was not demonstrated, the combination of unauthenticated access, large-scale enumeration, and credential disclosure was sufficient to warrant a High severity rating and immediate remediation.
